## 1. Compound compliance (.claude/rules/compound-component-structure.md)

Compliant — the strongest lazy-boundary discipline in this audit batch. Both cross-registry heavy
deps are correctly `React.lazy`'d at the registry-lookup level, not just at the assembly level:
`lib/default-registry.ts:23` (`LazyFieldCode = lazy(() => import("../parts/field-code"))`) and
`:27` (`LazyFieldRichtext = lazy(() => import("../parts/field-richtext"))`) — so `@ilinxa/code-block`
and `@ilinxa/rich-text-editor` only enter a consumer's bundle if their schema actually uses a
`code`/`richtext` field. The devtools panel body (`parts/json-form-devtools-body.tsx`, 297 LOC) is
also lazy-boundary-isolated (`parts/json-form-devtools.tsx:23`) and gates to `null` in production.
`JsonFormProvider` is a real headless Root (`json-form-context.tsx`), and the standalone parts
(`JsonFormField`, `JsonFormSubmitButton`, `JsonFormResetButton`, `JsonFormErrorSummary`,
`JsonFormFieldWrapper`) all resolve through it. No findings.

## 2. Dead / orphaned public API

None found. All sub-exports (`index.ts`) are either mounted by the default `JsonForm` assembly or
documented as the headless composition surface. `useJsonFormHasSubmitted` is exported without an
individual usage.tsx callout, but the general headless-composition pattern is documented in depth
(§"Headless usage") and the guide (`docs/procomps/json-form-procomp/json-form-procomp-guide.md`)
covers the full API — doesn't clear the "abandoned surface with evidence" bar.

## 3. Undocumented prop semantics

None found. `usage.tsx` doesn't walk through the imperative handle (`submit`/`reset`/`setValue`/
`getValue`/`setError`/`trigger`/`focus`/`isDirty`/`isValid`/`isSubmitting`), but the guide
(`json-form-procomp-guide.md:370-388`, "## Imperative API") documents every method with examples —
this is the established split in this codebase (usage.tsx = quick start, guide = full reference),
not a gap. `useImperativeHandle(ref, () => handle, [handle])` (`json-form.tsx:106`) confirms the
handle is a real, live implementation, not a stub.

## 4. A11y baseline

Mostly solid and matches `meta.ts`'s detailed a11y claims (deterministic `useId()` field ids,
`ariaProps` bridge, `role="alert"` error summary, focus-to-first-invalid-field on submit failure,
`role="radiogroup"` rating widget with arrow/number/Home/End keys — all spot-verified in
`parts/field-rating.tsx:26-63`).

**Finding:** `JsonFormDevtools`'s default keyboard shortcut is literally `"Ctrl+Shift+J"`
(`parts/json-form-devtools.tsx:49`, wired via `matchesShortcut()` in
`parts/json-form-devtools-body.tsx:319-320`). That exact combination is Chrome's and Edge's own
reserved shortcut for opening the browser's JavaScript console (on Windows/Linux) — browsers treat
it as non-overridable, so in the two most common browsers this default binding will open the browser
console instead of (or in an unpredictable race with) the intended panel toggle. The `shortcut` prop
is overridable, but the shipped default silently collides with browser chrome in the majority
environment.

## 5. Weight & slice candidacy

Core folder (excl. `demo.tsx`/`dummy-data.ts`/`usage.tsx`/`meta.ts`): **4,424 LOC**, spread evenly
across 25 field renderers + the compilation engine — no single file exceeds 10% (`json-form.tsx` 426,
9.6%; `lib/schema-compiler.ts` 396, 9.0%). No feature-slice candidate: the two genuinely heavy
sub-systems (code/richtext field renderers, devtools panel body) are already behind `React.lazy`
boundaries per §1. The remaining weight is the core schema-compilation/conditional/computed engine,
which every consumer needs regardless of which of the 25 field types their schema actually uses —
there's no coherent opt-in axis left to extract.
