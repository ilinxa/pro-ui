verdict: findings-logged

## 1. Compound compliance (.claude/rules/compound-component-structure.md)

Internally, `task-tree` is a strong example of the rule's intent: three purpose-separated contexts
(`TaskTreeStateContext` / `TaskTreeRenderContext` / `TaskTreeDndContext`,
`hooks/use-task-tree-context.ts:27,72,118`, each with a doc-commented "how to compose parts/
manually" contract) and **19** correctly, flatly named `TaskTree<Region>` parts under `parts/`
(`TaskTreeToolbar`, `TaskTreeList`, `TaskTreeRow`, `TaskTreeDragOverlay`, `TaskTreeBulkActionBar`, …
— confirmed via grep, all top-level `export function`/`export const`). This is close to the Tier
B/C shape the rule asks for.

**Finding:** none of those 19 parts are re-exported from `index.ts` — the barrel exposes only
`TaskTree`, `TaskTreeWithEditor`, and the headless `useTaskTreeState` hook. The only supported
composition surfaces for a partial layout are the 8 `render*` slot props and the headless hook —
there is no way for a registry consumer to import `TaskTreeToolbar` or `TaskTreeList` on their own
without reaching past the public barrel into internal file paths. This isn't inherited debt: the
context/parts design was built in the v0.2.0–v0.3.0 window
(`docs/procomps/task-tree-procomp/reviews/2026-06-18-v0.2.0-spotcheck.md`,
`2026-06-23-v0.3.0-spotcheck.md`), i.e. **after** the compound rule's 2026-06-10 establishment date,
so the barrel gap is a current-era miss, not grandfathered history.

Separately, `@dnd-kit/core` (`task-tree.tsx:12-16`, `hooks/use-tree-dnd-internal.ts:13`,
`parts/task-tree-grip.tsx:3`, `parts/task-tree-row.tsx:3`) and `@tanstack/react-virtual`
(`hooks/use-tree-virtual.ts:3`) are imported statically, not `React.lazy`'d, even though
virtualization is explicitly conditional at runtime ("auto-enables at ≥200 items" per `meta.ts`)
and DnD already has an `internal`/`external` mode switch (`dndContext` prop) suggesting the authors
already modeled it as an optional capability.

## 2. Dead / orphaned public API

None found. All 19 unexported parts are actively used internally by `TaskTreeList`/`TaskTree`
itself (this is the barrel-export gap in §1, not an abandoned-surface case — every part is reachable
through the default assembly). `TaskTreeWithEditor` and `useTaskTreeState` are both exported and
both documented in `usage.tsx`.

## 3. Undocumented prop semantics

The shipped v0.3.0 clipboard capability — `copyItems`/`cutItems`/`pasteItems` (3 of the handle's 29
methods, `types.ts:232-236`), the document-level ⌘/Ctrl+C·X·V bindings, and cross-surface
`ilinxa/task` envelope interop with `task-card`/`card-tree`/`gantt-timeline` (all called out in
`meta.ts:28`) — has **zero** coverage in `usage.tsx`: its "Imperative handle" section (line 90)
is headed *"(26 methods)"* and its code sample stops at `clearAllFilters` (`usage.tsx:90-129`),
3 short of the real 29-method surface. The guide
(`docs/procomps/task-tree-procomp/task-tree-procomp-guide.md:574`) is not a backstop here either —
its own "v0.3" roadmap entry describes a *different, still-unshipped* item ("Server-rendered initial
state... currently full client-side"), meaning the guide was never refreshed after the real
v0.3.0 ship landed. The `priorityOptions` prop (`meta.ts:29`, threaded to `TaskTreeWithEditor`) is
likewise absent from both docs surfaces. This clears the section's "absent from usage.tsx AND the
guide" bar for a full shipped feature class, not just a prop nuance.

## 4. A11y baseline

Solid — full ARIA tree contract on the list container (`role="tree"`, `aria-multiselectable`,
`role="treeitem"`, `aria-level`, `aria-expanded`, `aria-selected`, `parts/task-tree-list.tsx:118-220`)
across all three render branches (virtualized / windowed / plain). No findings.

## 5. Weight & slice candidacy

Core folder (excl. `demo.tsx`/`dummy-data.ts`/`usage.tsx`/`meta.ts`): **5,546 LOC**. Top-3 files:
`hooks/use-task-tree-state.ts` 492 (8.9%), `task-tree.tsx` 452 (8.2%), `lib/reducer.ts` 395 (7.1%).

No axis clears the ≥20% LOC bar for slice candidacy — reported honestly rather than forced. The two
closest: DnD (`hooks/use-tree-dnd-internal.ts` + `use-tree-dnd-html5.ts` + `task-tree-grip.tsx` +
`task-tree-drop-indicator.tsx` + `task-tree-drag-overlay.tsx` + `lib/edge-zone.ts` +
`lib/circular-drop.ts` + `lib/dnd-payload.ts` ≈ 664 LOC, ~12%) and the default toolbar/filter/sort/
search stack (`task-tree-toolbar.tsx` + `task-tree-filter-dropdown.tsx` + `task-tree-sort-dropdown.tsx`
+ `task-tree-search-input.tsx` + `task-tree-filter-active-toggle.tsx` + `task-tree-bulk-action-bar.tsx`
+ `lib/filter-items.ts` + `lib/sort-items.ts` + `lib/search-items.ts` ≈ 821 LOC, ~14.8%) are both
sub-threshold. **Not a feature-slice candidate at this size** — not enough distinct, low-base-coupling
weight in one axis to justify a `task-tree-<feature>` split; the compound-barrel gap in §1 is the more
actionable win.
