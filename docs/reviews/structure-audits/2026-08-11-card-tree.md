# Structure audit — card-tree v0.5.0 (2026-08-11)

verdict: findings-logged
artifact: 276.2 KB / budget 320 KB (13.7% headroom)

## 1. Compound compliance (.claude/rules/compound-component-structure.md)

**Findings.** `CardTree` (`card-tree.tsx`) is a single monolithic `forwardRef` component (1,297 LOC)
that owns all state (`useReducer`), all dispatchers, all DnD wiring, and all imperative-handle
logic in one file — there is no headless `Root` provider and no `createContext`/`useContext`
anywhere in the folder (confirmed via grep). Parts under `parts/` (`Card`, `FieldRow`,
`PredefinedRenderer`, …) receive their behavior through a single prop-drilled `config: CardConfig`
object threaded recursively through `Card` (`parts/card.tsx:196-206` → `parts/card.tsx:442-449`
re-passes `config` into every recursive child) rather than reading `use<Name>()` context — the
opposite of the rule's "no prop-drilling, assembly is declarative" requirement.

Separately, `@dnd-kit/core`, `@dnd-kit/sortable`, and `@dnd-kit/utilities` are imported
**statically** at module scope (`card-tree.tsx:13-21`; `parts/card.tsx:4-5` for `useSortable`/`CSS`)
and are not `React.lazy`'d. `editable` (and DnD specifically) is exactly the kind of optional
capability the rule calls out ("a reasonable consumer would want a subset" — a read-only viewer) —
today every consumer, including read-only ones, pays the 3-package DnD bundle weight.

Both are real trigger conditions (heavy dep not every consumer needs; a plausible read-only subset)
under the rule's "When it applies" list. `card-tree`'s functional development (v0.1–v0.4, per
`docs/procomps/card-tree-procomp/`) predates the rule's 2026-06-10 establishment date, and it has
had no functional touch since (the 0.5.0 bump today is the `artifactBudgetKB` metadata sweep only,
per `meta.ts` `context` field) — so this is logged as inherited structural debt, not a violation of
a rule in force at build time.

## 2. Dead / orphaned public API

`BulkToolbar` (`parts/bulk-toolbar.tsx`) and `computeSelectionStats` (`lib/bulk-actions.ts:83-116`,
explicitly commented "for bulk-toolbar display") are fully built (count/duplicate/delete/set-field/
toggle-lock UI, all with `aria-label`s) but: not exported from `index.ts`, not imported/mounted in
`card.tsx` or `card-tree.tsx` (confirmed via grep — zero references outside its own file), and not
mentioned in `usage.tsx` or the guide (`docs/procomps/card-tree-procomp/card-tree-procomp-guide.md`).

This is more than an unmounted à-la-carte part: 3 of its 4 action callbacks
(`onDuplicate` / `onBulkSetField` / `onToggleLock`) have **no backing implementation at all** — the
reducer (`lib/reducer.ts`) only implements a `"bulk-remove"` action type (`lib/reducer.ts:131,739`),
and even that is never dispatched anywhere in `card-tree.tsx` (no dispatcher function, no
`CardTreeHandle` method). Meanwhile `meta.ts:21` advertises this as a shipped v0.3 feature:
*"Multi-select with shift-click range + cmd-click toggle; bulk delete / duplicate / set-field /
toggle-lock."* A consumer following the docs cannot reach 3 of these 4 operations through any public
API — this is an abandoned surface with hard evidence, not a legitimate unmounted à-la-carte part.

## 3. Undocumented prop semantics

None found beyond the staleness noted in the Owners table — `usage.tsx` is intentionally a thin
"quick start" and the full v0.2–v0.4 prop surface (permissions, search, DnD, undo, validators) is
documented in `docs/procomps/card-tree-procomp/card-tree-procomp-guide.md` §§5-9 (not re-read in
full here, spot-checked at the top matter). The guide's own header still reads *"Aligned with
shipped v0.4.0"* while `meta.ts` is now `0.5.0` — see Owners.

## 4. A11y baseline

Keyboard tree nav (`hooks/use-tree-keyboard.ts`) and inline-editor focus-on-enter (grep for
`.focus()` across `field-edit.tsx`, `meta-edit.tsx`, `card-title-edit.tsx`, `predefined-edit.tsx`
all move a ref into focus on mount) are solid — no findings there.

One real finding: `PredefinedRenderer` (`parts/card.tsx:169-178`) wraps the **entire rendered
predefined block** — including a full `<table>` for the `table` predefined key
(`parts/predefined-table.tsx:33-67`, real `<thead>`/`<tbody>`/`<tr>`/`<th>`/`<td>`) — inside a
`<button type="button">` as the click-to-edit affordance whenever `editable` is true. `<table>` and
`<ul>` (the `list` predefined block) are flow content, not phrasing content, so nesting them inside
`<button>` is invalid per the HTML content model; in practice this collapses the table's row/column
structure into one flattened accessible name, so screen-reader users lose per-cell navigation on an
editable `table` block.

## 5. Weight & slice candidacy

Core folder (excl. `demo.tsx`/`dummy-data.ts`/`usage.tsx`/`meta.ts`): **8,024 LOC**. Top-3 files:
`card-tree.tsx` 1,297 (16.2%), `lib/reducer.ts` 857 (10.7%), `parts/card.tsx` 444 (5.5%).

**Slice-candidate axis: the inline-editing layer.** `field-edit.tsx` + `predefined-edit.tsx` +
`meta-edit.tsx` + `field-add.tsx` + `card-title-edit.tsx` + `lib/validate-edit.ts` +
`hooks/use-edit-mode.ts` + `card-actions.tsx` + `predefined-add-menu.tsx` + `inline-error.tsx` +
`field-row.tsx` + `meta-inline.tsx` + `meta-popover.tsx` + `card-header.tsx` = **2,358 LOC (29.4%)**
— a coherent, well-named capability ("click-to-edit + validation + permission-gated edit
affordances") that a read-only-viewer consumer (agent-transcript viewer, ADR viewer) plausibly never
needs. Base-coupling is medium, not low: `parts/card.tsx` conditionally renders these parts inline
behind `config.editable` checks rather than a lazy boundary — the same "MIXED-chunk extraction"
topology the P3 plan already logged for `event-calendar`'s edit axis. The DnD axis (~300 LOC, ~3.7%
— `hooks/use-dnd-config.ts` + `parts/drag-handle.tsx` + `parts/drop-indicator.tsx` +
`lib/dnd-helpers.ts` + inline DnD wiring in `card-tree.tsx`/`parts/card.tsx`) is too small alone to
clear the ≥20% bar, but is only ever exercised when `editable` is true — it belongs inside the same
prospective editing slice (bundling the `@dnd-kit` weight out of base with it), matching the
injection-surface convention P3 ratified for its pilots (base owns extension context + `editable`
prop; feature module supplies the edit/DnD implementation).
