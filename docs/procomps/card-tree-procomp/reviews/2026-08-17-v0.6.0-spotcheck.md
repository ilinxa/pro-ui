## Origin

An external consumer report (*"Custom Keys Are Inert"*, from JSON CMS / `simple-cms`) against
0.5.0. `customPredefinedKeys` was declared on `CardTreeProps`, documented in guide §7.1 with a
copy-pasteable example, and listed in the `types.ts` header as a delivered v0.3 capability — but
**nothing between `parse` and the renderers ever read it**. A registered block silently rendered as
an ordinary nested card and round-tripped correctly, so the integration looked like it worked. No
console warning, no parse error, no type error. The report's diagnosis cost a day.

All four reported findings were verified against source before intake; every line reference in the
report was exact. Four more (F5–F8) were found during intake, and eight more during review.

## Verdict: **Pass with follow-ups**

Closes GATE 3. Rationale: all close conditions hold (below); 16 review-surfaced findings were
resolved or explicitly refuted; the headline invariant is proven three independent ways
(pure-logic fixed point, consumer compile, live production render). Remaining follow-ups are
owned, none blocking.

## What this says about the process

The bug shipped because **no gate can see a wired-but-inert prop**. It typechecked, linted, and
passed `validate:meta-deps` for three minor versions. The only artifacts that would have caught it
are a demo that mounts the feature and a round-trip test — neither existed. Both now do.

Two findings this run were invisible to every producer-side gate and were caught only by using the
component as a consumer would: the permission-matrix type gap (U5 probe) and the non-resolving
import path in the docs (finder 2). That is the argument for keeping the consumer probe in the
smoke, not just the install.
