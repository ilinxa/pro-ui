## Origin

FU-2 from card-tree's v0.6.0 review, one day old. Logged as *"`card-tree-node` renders custom blocks as nothing."*

**The logged finding understated the defect.** A probe against v0.3.0 before any fix showed six block keys vanishing, not two:

```
VANISHED    : ["image","table","codearea","list","body","metric"]
LEAKED->FIELD: ["quote"]
```

The four built-in blocks were never logged, and `quote` — a string-valued built-in — was being absorbed into the flat-field strip where it could displace a real field. FU-2 described a symptom of a single root cause: the viewer had no key router at all, only two independent value-shape tests, and a card-tree *block* fails both by construction.

## Rigor note — why no fresh finder agent

The ladder's `minor` row calls for one fresh finder over the diff plus the dependents axis. Two things replaced it, deliberately:

1. **The dependents axis is empty and that was verified, not assumed.** Nothing in `registry.json` depends on `card-tree-node` except its own fixtures item and `rich-card-in-flow`, which is a 0-file deprecated rename alias. No `meta.featureOf` targets this base. No cross-procomp source imports it.
2. **The test tier landed the day before and is a stronger instrument than a finder here.** The defect class is "renders as nothing" — exactly what an assertion catches and a reading pass misses; FU-2's parent bug survived three minor versions of human review precisely because it typechecked and linted. The tests were written *before* the fix, watched failing, and re-falsified afterwards by neutralising the fix.

This is a deviation from the ladder and is recorded as one. It would not be appropriate for a change with live dependents.

## What this says about the process

FU-2 was logged one day earlier by the review of the *sibling* component, and it named two of the six affected keys. The full defect only surfaced by running a probe against the real code before writing any fix — the intake step that FU-2 itself never had. **A logged follow-up is a lead, not a specification.**

The most valuable finding this run (a host capturing a built-in key) came from a test written before the implementation, and failed on its first execution. The second (silent truncation past the cap) came from the production-build e2e run, invisible to every other gate — the demo simply had one more block than the default cap, and nothing said so. Both are the same lesson card-tree v0.6.0 closed with: nothing but mounting the feature and asserting on it can see this defect class.
