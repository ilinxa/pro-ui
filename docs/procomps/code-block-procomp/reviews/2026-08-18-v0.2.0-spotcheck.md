# Readiness review — `code-block` v0.2.0 (spotcheck, API-touching minor)

- **Date:** 2026-08-18
- **Tier:** pro-component
- **Trigger:** public-API-touching minor (`.claude/rules/readiness-review.md` trigger table)
- **Scope:** implement the two documented-but-missing soft-failure modes; make the regex engine selectable; document the wasm/CSP requirement
- **Reviewer:** architect (main session), AI-assisted — 1 fresh adversarial finder (ladder rigor for `minor`), dependents axis included
- **Loop record:** [`code-block-loop.md`](../code-block-loop.md)

---

## Origin

An external consumer report (*"The Soft-Failure Gap"*, JSON CMS / `simple-cms`) against 0.1.4. The
integrator's own CSP (`script-src 'self'`, no `'wasm-unsafe-eval'`) blocked Shiki's WebAssembly
engine, which is entirely their side — but the consequence was ours: **every code block rendered as
an empty panel, nothing on screen and nothing in the console**, and it cost them about an hour to
diagnose. A block that had shown the code unhighlighted would have made it obvious in seconds.

Re-validated against HEAD before intake; every line reference in the report was exact.

**The report also under-reported itself.** Its own table marked the CodeMirror init-failure fallback
"✓ recoverable". That fallback did not exist: `hooks/use-code-mirror.ts` had no `catch`/`throw`/
`Error` in 241 lines, and `mount()` was a floating `void mount();` — a failed grammar chunk gave an
unhandled rejection over a blank editor, the *same* failure shape on the other mode. So the honest
count was **2 of 4 documented soft-failure modes unimplemented, not 1 of 4**.

## Verdict: **Pass with follow-ups**

Closes GATE 3. All close conditions hold; three review findings were confirmed and fixed with
regression tests, each falsified; the headline behaviour is proven by mounting the real component
against a genuinely failing dependency, not by inspection.

## What shipped

| # | Change | Why it is not cosmetic |
|---|---|---|
| 1 | **View-mode plaintext fallback.** No highlight HTML ⇒ render the raw code as per-line rows; body carries `data-highlight="ready" \| "pending" \| "failed"`. | Covers the pre-paint state *and* permanent engine failure with one path. The reported bug becomes a cosmetic degradation, which is what the rest of the component already promised. |
| 2 | **CodeMirror init-failure recovery.** `void mount()` now catches; `error` state renders `role="alert"` + a **"Reload as view-only"** control that swaps in the view body. New labels `editorFailed`, `reloadAsViewOnly`. | Removes an unhandled rejection *and* implements the fallback the docs had claimed since v0.1.0. |
| 3 | **Selectable regex engine** — `regexEngine?: "oniguruma" \| "javascript"`, cached per engine, evicted on failure. | `javascript` needs no wasm at all, so a CSP-restricted host can opt out instead of widening its policy. |
| 4 | **CSP documented** — description *Runtime requirements* + a `usage.tsx` section. | Zero mentions of CSP/wasm existed anywhere. This is the ask that would have saved the integrator's hour. |

## Findings

One finder, seven axes. Three CONFIRMED (all mine, all introduced by this change or exposed by it),
four axes clean on hard evidence — including a probe that reproduced Finding 1 against the *real*
module rather than test doubles.

| # | Finding | Failure scenario | Verdict | Fix + regression test |
|---|---|---|---|---|
| 1 | **Cross-engine language cache** (High). Module-global `loadedLangs` Set consulted *before* the per-instance check. | Two blocks on a page, `lang="rust"`, different `regexEngine`. The second short-circuits on the first's bookkeeping, never calls `loadLanguage` on its own highlighter, and throws ``Language `rust` not found`` on the next tokenize — surfacing as a **permanent plaintext fallback on a perfectly healthy engine**. Finder reproduced it live. | **CONFIRMED** | Set deleted; `highlighter.getLoadedLanguages()` is now the only source of truth (per-instance, cannot drift). `review-regressions.test.tsx` R1 ×2 |
| 2 | **`editorFellBack` one-way trap** (High). Set true, never reset. | Host with an Edit/Preview toggle hits a transient mount failure, takes the recovery, later flips `mode` back to `"edit"` — nothing happens, ever. Only escape is a `key` remount, which nothing documents. | **CONFIRMED** | Reset when `mode` changes, via React's adjust-state-during-render pattern (an effect would trip the compiler's cascading-render lint). R2 |
| 3 | **Half-applied highlight in the fallback** (Medium). Fallback rows lacked `.line` / `data-highlighted`. | `highlightedLines={[3]}` under a blocked engine: the gutter *number* bolds (different component) while the row has no tint — an inconsistent highlight. | **CONFIRMED** | Rows now carry `.line` + `data-highlighted`, so the existing CSS applies. R3 |
| A | View body renders empty for non-empty `value` | none constructible — `splitToLines()` always returns ≥1 row; the only empty path is the explicit `value === "" && !streaming` guard | **DROPPED** | — |
| A′ | Fallback breaks gutter alignment | none — fallback utilities reproduce `pre.shiki .line`'s geometry values exactly (`block`, `min-h-[1.6em]`, `-ml-1`, `pl-1`); finder measured both paths identical | **DROPPED** | — |
| B | XSS / escaping via the fallback | none — `visibleHtml` only ever resolves to Shiki's own output; raw `value` renders as JSX children (React-escaped) and never reaches `dangerouslySetInnerHTML` | **DROPPED** | — |
| C | Engine-cache race / eviction bug | none — eviction `.catch()` attaches before any caller awaits, doesn't rethrow, and doesn't swallow the original rejection; no-arg call still behaves exactly as 0.1.x | **DROPPED** | — |
| E | Dependents regression | none — `json-form` and `media-library` use only the stable prop surface; `CodeBlockLabels` stayed `Partial<>`, so two new optional keys break no assignability | **DROPPED** | — |

## Pre-mortem

If this breaks for a consumer, it breaks because they mix two `regexEngine` values on one page with
a lazy-loaded language and hit some *other* per-instance state I did not find — Finding 1 was
exactly that shape, and the fix removed the only global I could see. The regression test pins the
language path specifically; anything else per-instance would be a new discovery.

## Addendum — 2026-08-18 (post-verdict)

**Close condition 1 is now satisfied.** `code-block-procomp-guide.md` was authored as a docs pass,
closing FU-1; the planning trio is complete for the first time. The verdict above
(*Pass with follow-ups*) is unchanged — this records the follow-up closing, not a re-review.

Writing the guide surfaced **two more inert public surfaces** (FU-6, FU-7), both logged above. Both
had been deferred *to v0.2.0* in the planning docs, and v0.2.0 shipped without either while the
types and `meta.ts` continued to advertise them. This is the third instance in a fortnight of the
same class — after `card-tree`'s `customPredefinedKeys` and this release's own CodeMirror fallback
— and it is now clear that **authoring the consumer-facing guide is itself a detector**: writing
“here is how you use X” is the step that forces a check of whether X does anything.
